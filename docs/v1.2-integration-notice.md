## v1.1 changes v1.2 must preserve

### Runtime / startup

- Restore compatibility for the removed legacy scope selectors (`projectSelect`, `worldSelect`, `branchSelect`) so workspace/library startup does not fail with `Cannot set properties of null (setting 'innerHTML')`.
- Preserve the generation draft-key fix so `generateStory()` reaches `/api/generate/stream` instead of failing before the request.
- Keep runtime-oriented regression coverage; syntax-only JS checks were insufficient to catch these failures.

### Library lifecycle

- Bulk Library selection now has a recoverable **Trash** path rather than only Move / Collection / Archive / Clear.
- Bulk Trash uses `/api/lifecycle/trash`; permanent deletion remains exclusive to the Trash/Activity Center flow.
- Ctrl+Z can restore the successful resources from a bulk Trash operation.
- Stale selected family/variant context references are removed when those resources are trashed.

### Quick Create completion

The v1.1 completion pass expands Quick Create beyond top-level resource classes.

`Create as` exposes explicit subtypes:

- Library: Character, Location, Item, Organization, Lore, World Rule, Relationship
- Manuscript: Scene, Chapter, Note, Research, Outline
- Workspace: World, Project, Project Folder

Explicit subtype selection maps onto the existing backend fields (`forced_kind`, `entity_type`, `document_type`) rather than introducing a second schema.

### Destination / ownership

Quick Create now makes destination explicit instead of assuming that navigation location equals ownership/context:

- Project
- World
- Branch
- Library folder or project folder where applicable

Preserve the architectural separation:

**navigation != ownership != model context**

A resource being opened or created in a destination must not silently mean it is automatically injected into model context.

### Relationship Quick Create

Relationship creation is now treated as a first-class Quick Create flow using existing entity variants:

- subject
- relation type
- object
- world / branch scope

The resolver should prefer/require existing Library identities and must not silently create duplicate characters/entities just to satisfy a relationship parse.

## Implications for v1.2 architecture

When implementing v1.2 memory and reasoning systems, assume the corrected v1.1 boundaries above:

- Library resources have explicit lifecycle semantics.
- Project files and Library knowledge remain separate ownership domains.
- World/branch scope is explicit and must survive forks/what-if workflows.
- Context selection is intentional and explainable, not equivalent to browsing/opening a resource.
- Relationships are first-class semantic objects and should feed temporal state, consequence reasoning, and retrieval.

Recommended v1.2 dependency direction:

```text
Temporal / Episodic Memory
          |
          v
State + Relationship Model
          |
          v
Consequence / Continuity Reasoner
          |
          v
Context Retrieval + Compiler
          |
          v
Inference Model
```

Do not begin by bolting a generic RAG index onto the old v1.1 base. Integrate the corrected foundation first, then let retrieval consume scoped semantic state, temporal episodes, relationships, and explicit user context.
