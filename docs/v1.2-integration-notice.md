## v1.1 behavior v1.2 must preserve

### Runtime / startup

- The removed legacy scope selectors (`projectSelect`, `worldSelect`, `branchSelect`) can no longer crash workspace/library startup with `Cannot set properties of null (setting 'innerHTML')`.
- Generation must reach the generation endpoint; the missing `sentDraftKey` regression must not return.
- Runtime-oriented frontend tests are required; syntax-only JavaScript validation did not catch these classes of failure.

### Library lifecycle

- Bulk Library selection includes recoverable **Trash**, not only Move / Collection / Archive / Clear.
- Bulk Trash uses `/api/lifecycle/trash`; permanent deletion remains an explicit Trash/Activity Center action.
- Ctrl+Z restores successfully trashed resources from the most recent bulk operation.
- Trashing selected families removes stale selected family/variant references from model-context selection.

### Quick Create completion

`Create as` now exposes explicit user-facing subtypes instead of only top-level resource classes:

- Library: Character, Location, Item, Organization, Lore, World Rule, Relationship
- Manuscript: Scene, Chapter, Note, Research, Outline
- Workspace: World, Project, Project Folder

These selections map onto the existing backend contract (`forced_kind`, `entity_type`, `document_type`) rather than creating a duplicate schema.

### Explicit destination / ownership

Quick Create can explicitly target:

- Project
- World
- Branch
- Library folder or Project folder where applicable

Preserve this boundary:

**navigation != ownership != model context**

Opening, browsing, or creating a resource in one place must not silently mean that resource is injected into inference context.

### Relationship Quick Create

Relationships are first-class semantic resources with:

- subject
- relation type
- object
- world / branch scope

The Quick Create resolver uses existing Library identities/variants and must not silently generate duplicate characters/entities just to satisfy a relationship parse.

This is important for v1.2: relationship dynamics, temporal state, consequence reasoning, retrieval, and memory should consume the same first-class relationship objects rather than inventing a parallel representation.

## v1.2 architectural assumptions after integration

Once `develop/v1.2` has absorbed current `main`, treat these as foundation invariants:

- Library resources have explicit lifecycle semantics.
- Project files and Library knowledge remain separate ownership domains.
- World/branch scope is explicit and must survive forks, what-if branches, snapshots, and later memory retrieval.
- Context selection is intentional and explainable rather than equivalent to browsing/opening a resource.
- Relationships are first-class semantic objects.
- Retrieval should be downstream of semantic/temporal state rather than replacing state with a vector index.

Recommended dependency direction remains:

```text
Temporal / Episodic Memory
          |
          v
State + Relationship Model
          |
          v
Consequence / Continuity Reasoner
          |
          v
Context Retrieval + Compiler
          |
          v
Inference Model
```

Do not start v1.2 by bolting generic RAG onto the old frozen-v1.1 tree. First integrate `main@ee1265f3c8cf3a391eafcfc1fb0831f9ca51a0f1` (or a later descendant), then let retrieval consume scoped semantic state, temporal episodes, relationships, explicit user context, and later multimodal evidence.
